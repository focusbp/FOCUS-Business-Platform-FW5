# 管理アプリ起点のマスターログイン設計

状態: テスト実装・検証済み。共通フレームワークは2026-11-16に本番配布済み（e2751ab）。管理アプリの本番配布・本番有効化は未実施。

2026-11-16改訂: 利用者の「既存db_apiの通信を使い、複雑にしない」という指定を反映。この文書が旧版の専用署名鍵・公開鍵配布・postMessage照合方式を置き換える。本番の認証設定変更・実アカウント操作・配布は未実施。テスト側では既存の資格情報を再利用した設定を配置した。

## 方針

既存db_apiで使うHTTPS＋HMAC通信、台帳のAPI Key/Secret、既存のワンタイム認証・セッション管理を再利用する。Web処理からローカルのdb_api.shを起動するのではなく、同じHTTP/HMAC仕様のPHP処理を使う。

新しい公開鍵方式、SSO製品、専用秘密鍵の配備、ブラウザーのpostMessage連携、状態ポーリングは追加しない。

一方、通常API Key/Secretを持つだけでは、呼出し元がapp-soshikikaikakuであることは分からない。このため「管理アプリが発行した短期許可を、受信先が管理アプリへ確認する」処理を1つ追加する。アプリ名の自己申告やRefererだけでは発行元を認証しない。

## 利用条件

- 発行操作はapp-soshikikaikakuの有効なマスターアカウントに限定。通常ログイン済みで操作でき、ボタンごとに追加パスキー操作は求めない。
- 発行元の管理セッション、user/epoch、CSRFを検証。一時ログインからの再委譲は許可しない。
- 対応先は共通login/user/passkey/password_resetを使うアプリ。独自認証や追加認証ガードのあるアプリは個別対応まで拒否する。
- 宛先は選択した台帳からサーバー側で決める。任意URL・任意ユーザーIDは受け付けない。
- 受信先のマスターは受信先でuserの最古IDを調べ、type=0かつstatus=0を確認する。ID=1やログインID文字列を固定しない。無効な場合、次の管理者へ切り替えない。
- テスト管理アプリから本番への発行は禁止。本番・テスト・アプリパスを含む実配置単位で許可を結び付ける。code_dirだけでは識別しない。

## 操作の流れ

1. 管理画面で「マスターアカウントでログイン」を押す。クリック時に別タブを確保する。ポップアップ拒否なら処理を止めて案内する。
2. 管理アプリが権限・CSRF・台帳を確認し、60秒有効のランダムな許可番号を発行する。許可番号は選択したアカウント・環境・操作ユーザー・epochに結び付ける。
3. 管理アプリのサーバーが、既存の宛先API Key/Secretで受信先の準備APIを呼び、許可番号をPOSTする。この段階のHMACだけではログイン券を発行しない。
4. 受信先サーバーが、設定済みの固定の管理アプリ照会先へ許可番号を確認する。管理アプリが発行済み・対象一致・期限内・未消費であることを照合して許可を消費する。確認成功後だけ、受信先が1回限りのログイン券を作って管理アプリへ返す。
5. 管理画面がログイン券を、固定の受信先ログイン画面へ別タブのフォームPOSTで渡す。URLには付けない。APIキー・パスワードはブラウザーへ渡さない。
6. 受信先は自分のCSRF付きフォームを作り、同一Originへ自動POSTする。券・CSRF・Origin・期限・未消費・マスターの現状を確認し、通常の管理セッションを開始する。コード入力・ログイン先のパスキー操作は不要。

既存onetimecode画面へクロスサイトPOSTするだけでは、現在のCSRF/Origin条件を満たさない。その条件は緩めず、この専用入口から受信先内の同一Originフォームへ移す。

## サーバー間の確認方法

追加の共通管理APIキーを各アプリへ配らない。

- 管理アプリ→受信先: 受信先の既存API Key/SecretでHMAC認証。
- 受信先→管理アプリ: 受信先自身の同じAPI Key/SecretでHMAC署名。管理アプリは許可番号に結び付く台帳から期待するキーを取得し、照合する。
- 管理アプリの照会APIは、通常の管理アプリAPIキーによるDB操作口とは別の専用処理にする。許可番号・台帳・署名を照合して結果だけ返し、台帳や秘密情報を返さない。
- 照会先は受信先の配備設定で固定し、リクエストで渡された確認URLへ接続しない。台帳のAPIキーが受信先と不一致なら失敗として扱う。
- 通信はHTTPS、証明書検証あり、リダイレクト追従なし。返却結果は要求した許可番号・宛先・環境と一致させる。

### 本文の保護

現行db_apiのHMAC対象はメソッド・パス・クエリ・時刻であり、本文そのものは含まない。

この機能の専用POSTでは、本文のSHA-256をクエリの `body_sha256` に入れ、既存のHMACでそのクエリを署名する。受信側で実際の本文ハッシュとの一致も必須にする。既存の署名アルゴリズムや通常DB APIの互換性は変えない。許可番号・ログイン券をクエリへ入れる代用はしない。

## 必要な追加と既存部分の再利用

| 部分 | 対応 |
| --- | --- |
| HTTP通信・HMAC | db_apiと同じ方式。PHP側の送受信処理を共通利用・整理する |
| 管理アプリの発行操作 | 台帳・権限・CSRFを確認し、短期許可を記録して受信先へ依頼 |
| 管理アプリの許可照会 | 宛先の既存API資格情報と許可番号を確認し、一度だけ消費 |
| 受信先の準備API | HMAC・本文ハッシュ・マスター確認、管理アプリへの照会、券の発行 |
| 受信先のログイン入口 | POSTされた券を同一OriginのCSRF付き自動フォームで消費 |
| ワンタイム認証 | 既存のハッシュ保存・単回消費・epoch確認・内部grant・セッション開始処理を再利用/共通化 |
| 固定の信頼設定 | 管理アプリの正規の照会先、環境、機能有効/無効のみ。公開鍵や新しい秘密鍵は不要 |

通常のCRUD用db_apiにログイン権限を持たせず、処理はログイン専用の入口に分ける。「同じものを使う」は通信・認証部品の再利用であり、DBのuserを読めたらログイン済みにする仕組みではない。

## 短期データと失敗時の扱い

- 管理アプリの許可、受信先のログイン券は、それぞれ乱数32バイト以上・60秒以内・1回限りとする。受信先の券は元の許可の期限を超えない。
- 通常保存はハッシュと紐付け情報だけ。生の許可番号・券は送受信時と画面への短期POSTにのみ使い、ログ・URL・クリップボードへ出さない。
- 記録する対象は元ユーザーID/epoch、台帳ID、受信先アカウント・環境・正規URL、受信先マスターのuser_id/user_handle/epoch、作成/期限/消費日時、操作識別子。
- 受信先が券を発行する前に管理アプリの許可を消費する。途中失敗では許可を未消費へ戻さず、ボタン操作からやり直す。成否不明時に自動で別券を増やさない。
- ブラウザーで券を消費する直前に、マスターが有効なままでuser_handle/epochも変わっていないことを再確認する。
- FFMで判定・更新を排他にし、独自flockは使わない。関係DBを先に開き、ネットワーク通信中はDBロックを保持しない。通信後は再読込して確定する。
- 専用固定fmtの許可・券は通常のDB API/MCPから読書きできないようにする。非表示メニューだけで保護した扱いにしない。
- 一般ユーザー、停止ユーザー、無関係な台帳、署名不正、期限切れ、既消費、環境不一致は拒否する。
- 旧案の「開いた元タブとの厳密なブラウザー同一性照合」は採用しない。券は短命な秘密情報であり、漏えいした有効な券が他ブラウザーで利用されないことまで保証する方式ではない。券のPOST受渡し・秘匿化・単回消費を必須とする。

## セッション

- ログイン後は最長30分、remember-meなし。
- 管理アプリによる委譲を `managed_master` として記録。既存onetimecodeと同じ一時認証の期限・再認証制限を適用する。
- 認証方式の文字列をPOSTで指定しても成立しない。許可確認と券消費を行った同じサーバー処理中だけの内部grantを必須にする。
- session ID更新、旧認証/CSRF/MCP認可途中状態の破棄、epoch検証、通常の画面権限を維持する。
- パスワード停止・既存パスキー設定を変更しない。鍵追加/削除等は従来どおり実パスキーで本人確認する。
- 元管理アプリのログアウトで、開始済みの受信先セッションが自動終了する機能は含めない。
- 既存のAI確認用onetimecodeは別用途として維持する。「管理アプリのみ」という制限は今回追加するボタンの発行経路に適用する。

## 完了確認

- 正常系: 通常ログイン済みの管理アプリのマスターから、本番/テストの指定先へコード・パスキー入力なしで入れる。
- 拒否: 管理アプリが許可していない通常APIクライアント、無効な許可番号、書換えた本文、別アプリ/環境、一般ユーザー、期限切れ・再利用を拒否する。
- 排他: 同じ許可・券の同時消費からログインが増えない。通信・セッション開始失敗後は新たなボタン操作が必要になる。
- ブラウザー: クロスサイトPOST→受信先の同一Originフォーム、CSRF、SameSite/Cookie Path、ポップアップ拒否、複数タブを確認する。
- 維持: パスキー設定・epoch・通常ログイン・既存onetimecodeを保持し、30分期限と鍵管理時の再認証を確認する。
- 秘匿: API設定HTMLにはAPI秘密情報を出さない。URL・アクセスログ・応答ログ・通常DB API/MCPに許可番号・券を出さない。券を一時的に含む専用POSTフォームはno-storeとし、既存のデバッグ出力・エラーログでも対象項目をマスクする。


## 実装済みの構成と設定

- 共通HTTP/HMAC: `lib/ManagedLogin.php`。既存の署名形式と本文SHA-256を併用する。
- 受信API: `managed_login_api::capability/prepare`。通常API認証だけでは券を発行せず、固定の管理アプリへ許可を照会する。
- 受信券とログイン: `login/ManagedMasterLoginService.php`、`login::managed_master`、`login/fmt/master_ticket.fmt`。中継フォームから受信先の同一Originへ自動POSTする。
- 管理アプリ: `sftp_master_login/Issuer.php`、`sftp_master_login::start`、`sftp_master_login_api::consume`、固定fmtの`permits`。
- 固定資格情報のDSP保護はアプリDSPのON/OFFより先に適用し、通常のDB APIから許可・券のCRUDを禁止。認証処理のサーバー内スコープだけでアクセスする。
- `managed_master` は一時認証としてログイン処理・セッション検証・鍵管理の再認証判定に組み込み済み。既存onetimecodeの形式と操作は保持した。

実配置の設定は `classes/data/_common/managed_login.php` に置くPHP配列。未配置または `enabled=false` では利用不可。コードリリースで秘密情報を含む設定ファイルを配布せず、配置先ごとに管理する。

| キー | 内容 |
| --- | --- |
| enabled | 有効か。明示的なtrueだけを許可 |
| environment | test / production |
| base_url | その実配置の正規ルートURL。fbp/app.phpやクエリを含めない |
| issuer_base_url | 固定の管理アプリ正規ルート。ブラウザー入力を接続先にしない |
| issuer | 管理アプリ側のみtrue。project_release_codeもapp-soshikikaikakuであることを検証 |
| allowed_base_urls | 管理アプリの登録済み独自ドメイン等を使う場合の明示的な追加ルート。PasskeyConfigのOrigin検証も必須 |
| test_root | 管理アプリ側のテストURLルート。各アプリのcode_dirを下に付ける |
| enabled_targets | 管理アプリが発行を許可する宛先の正規ルートURL一覧 |
| test_credentials | テストAPI資格情報が本番台帳と異なる場合の既存資格情報。宛先URL単位で指定 |
| http_basic | テストゲートウェイ等の既存Basic認証が必要な場合のみ、ホスト単位のusername/password。リダイレクトや別ホストへ転送しない |

API Key/Secretを新規発行・変更する設定ではない。ゲートウェイやAPIの既存資格情報を更新した場合は、この参照設定も追随させる。秘密を含む設定は所有者限定にし、ソース管理やログへ含めない。

現時点で有効化したのは、テストの管理アプリからapp-fwtestのテスト環境への組だけ。本番設定や他の受信先を自動で有効にしていない。
