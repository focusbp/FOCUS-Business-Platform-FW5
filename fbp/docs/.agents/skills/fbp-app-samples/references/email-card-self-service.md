# 公開メール確認・カード変更

管理一覧で発行した専用URLから、契約者がメールを確認し、メールアドレス・Squareカードを登録／変更する再利用サンプル。Standard Screenの行ボタンと独立した`sample_email_card_public`を使う。元アプリの料金プラン・紹介制度・案件・運用スクリプトには依存しない。

## 保存した流れ

- URLは対象・用途・期限・保存済みメールをHMACと暗号化で結び付ける。初回だけ受け、以降はセッションとCSRFで対象を解決する。単なる暗号化IDは権限にしない。
- メール登録済みなら、その保存済み宛先へ確認コードを送る。POSTの別アドレスへ本人確認コードを送らない。
- メール未登録なら、管理者が発行した専用URLを初期設定の権限として扱い、入力したメールのコード確認後に初めて保存する。URL漏洩時に初期設定され得る方式なので、既存アプリの本人確認方針と異なる場合はその方式を優先する。
- 本人確認後は、メールの右側に「メールアドレスを変更」、下部にカード操作を置く。新メールもコード確認前には保存しない。メール確定で旧URLは使えなくなるため、管理側で再発行する。
- コードは4桁・10分・誤入力5回、本人確認後の操作は10分、画面は30分、案内URLは30日という初期値。適応先の既存方針があれば合わせる。
- 中央寄せ・最大幅640px、淡いグレー背景・白いボックス・控えめな罫線・青い主操作。メール横ボタンを含め狭幅で横にはみ出させない。入力はFBP標準部品を使う。

## 重複送信はサーバーで扱う

同じ用途・同じ宛先の有効な確認情報があれば再利用する。二度目の操作でメールを再送せず、同じ確認画面を返す。有効期限・誤入力回数を延長／初期化しない。新しい送信が入力不備・回数制限・メールエラーで失敗しても、先に有効なハッシュを消さない。

ボタン無効化だけに依存しない。「確認コードが期限切れ」と表示されたら、期限だけでなく、再送失敗時の状態削除・二重送信・別タブの状態混同も確認する。検証は同一プロセスのメソッド呼出しだけで終えず、送信→別HTTP要求の重複送信→届いたコードの確認→保存／画面更新まで通す。

コード・専用URL・Squareトークンをログに出さない。保存するコードは`password_hash`だけ。コード画面には戻る・メール変更ボタンを置かず、入力エラーでは閉じない。成功時はpendingを消し、ダイアログを閉じて表示を更新する。

## カードと初回決済

標準動作はカード登録／差替えのみ。`Payment.php`は初回決済を無効にしてあり、ユーザーの依頼なしに料金を請求しない。

初回満額決済が指定されたときだけ、導入先の既存課金処理へ`SampleEmailCardPayment`を接続する。`initialEnabled()`と`ready()`を有効化し、`chargeInitial()`を実装したインスタンスを、公開クラスの`emailCardService()`から`SampleEmailCardProfile`へ渡す。初回は設定金額を表示して同額を請求し、差替え時は追加請求しない。未接続の有効化はSquareを呼ぶ前に停止する。

連携先は業務上の請求単位（例：契約＋請求月）で永続的な予約を作り、プロバイダーの冪等キーを使い、再送／月次処理と重なっても二重請求しないこと。結果は`state=success/failed/unknown/processing`で返す。成否不明を失敗と決めつけて再課金しない。元アプリの月次処理をテンプレートへ丸ごとコピーしない。

初回は`card_registered_at`と保存済みカードで区別する。既存契約へ適用するときは既存のカード履歴を使って初回扱いを整合させ、カード欄を消しただけで再度初回請求にしない。カード保存後の課金失敗でカードを消したり成功と表示したりしない。課金連携の実課金・履歴・並行実行の検証は導入先で行う。

Squareの空customer/cardは失敗とする。セッション・操作キー・期限・更新前のバージョンを検証し、外部APIの前にDBを閉じ、応答後に再オープン・再読込して競合を検出する。DB依存は先に開き、独自flockを追加しない。callbackの例外はSquareダイアログへ返す。

## 導入と接続点

[DB・メールと公開入口](email-card-self-service-db.md)を読み、次を分離して実行する。

```sh
php docs/.agents/skills/fbp-app-samples/scripts/install_email_card_self_service.php --code-root=<app-source-root>
# 環境の正規同期の後、対象テスト環境で定義を登録
php docs/.agents/skills/fbp-app-samples/scripts/install_email_card_self_service.php --configure-test-root=<test-runtime>
```

同名クラス・ノート・メールキー・定数があれば上書きせず適応する。実データ・SMTP/Square認証情報は配置しない。既存ノートへ適応する場合は、テーブル・項目・管理権限・組織別の絞込み・DSP依存を接続し直す。標準行ボタンには検索フォームの値も混ざるため、表示要求を保存要求と誤認して検索項目だけで拒否しない。実更新時の書込項目制限は維持する。

## 検証

`test_email_card_self_service.php <test-runtime> <temporary-parent>`は隔離FFMと模擬メール／Squareでコード保持・初回メール・変更・callback・任意課金フックを確認する。実メール・実決済はしない。

導入先ではさらに、公開URLのコピーと別タブ、本人確認前の個人情報非表示、通常フォームの入力保持、重複送信を含む別HTTP要求、確認後の閉じる／更新、640px中央配置と狭幅を確認する。初回課金を有効にした場合は、満額・差替え無課金・永続予約・失敗／成否不明・再送／月次の競合を外部処理を模擬して検証する。実課金を許可したことにはならない。
