# お客様と共有する移行手順

サイト移行の初回提案・着手案内では、対象範囲とともに下記の承認済み7手順を顧客向けコメントで提示する。AI自身も同じ番号で作業し、工程の完了・顧客への依頼・待機・再開・中断時には現在地を表示する。すでに共有・合意済みなら全手順や承認を繰り返さず、現在地・次工程・変更点を伝える。FOCUS等の会話上のサービス名を使い、ツール名やサーバー認証の詳細は顧客向け説明に持ち込まない。

## 基本形と許可の扱い

| 工程 | 作業と確認 | お客様との共有 |
|---|---|---|
| 1. TTLを120秒へ変更 | 変更可能なWeb用DNSレコードのTTLを先に120秒へ短縮し、変更前のTTLによる既存キャッシュの有効期限を確認する。接続先やメール用レコードは変えない | 【旧サイト表示中】。顧客作業なら設定を依頼し、変更できない場合は従来TTLによる切替への影響を説明する。TTL変更の確認・待機状況を記録し、依存しない収集や構築は進めてよい |
| 2. 調査・テスト構築 | 取得範囲を確認し、ページ・記事・素材・必要な機能をテスト環境へ再構築する | 【旧サイト表示中】。維持する範囲、取得できないもの、再現できないものを案内する。開発用URLを閲覧できると約束せず、環境の提供条件に合う確認資料を使う |
| 3. FBP本番への移行・目視確認 | 許可された範囲でバックアップ後、コードとページ・記事・画像等を本番へ取り込み、件数・内容・参照と実表示を確認し、お客様にも本番URLで見比べてもらう | 【旧サイト表示中】。DNS切替前にも本番配置・データ取込みが必要と説明する。本番禁止が残れば待つ。コード配布だけで完了にせず、確認URLと未対応部分を案内し、顧客の確認待ちも区別する |
| 4. 独自ドメインの事前設定 | 許可の下で、設置先にドメインの受け口・公開トップ・wwwの扱い・証明書取得用の経路等を用意し、DNS変更前の接続先指定で表示先を検査する | 【旧サイト表示中】。FBP本番取込みと事前設定が整う前にDNSの接続先変更を依頼しない。既存設定は再追加せず確認する。この準備は本番確認と並行してよい |
| 5. DNS切替 | 表示内容の確認と切替許可が揃ってから、必要なWeb用レコードと変更先を案内する。メール用設定を保持する | 【ここから一時的に表示できない可能性があります】。誰が変更するかを明示し、顧客作業なら変更後の返信を依頼する。旧サイト停止はこの手順に含めない。説明や本番配置承認だけでDNS変更まで許可されたと扱わない |
| 6. SSL設定 | 顧客作業の場合は完了返信を受け、DNS一致を確認し、必要な証明書発行・HTTPS/www転送を設定・確認する | 【切替作業中】。HTTPSで正常表示できるまで新サイトの公開確認済みとしない |
| 7. 新サイトの最終確認 | 独自ドメインのHTTPS・www転送・旧URL・画面・素材・必要な機能を確認する | 【新サイト表示中】。実際に確認した範囲と残作業、必要ならDNS反映待ちを報告する。noindexの解除時点は合意に従い、維持指示があれば解除しない |

通常の独自ドメイン設定の具体的な操作は環境の専用手順に従う。HTTP認証による証明書発行等、DNS切替後にしか完了できない工程があるため、「独自ドメインの準備」と「HTTPSでの最終確認」を分ける。Web用TTLの事前調整は環境手順で案内できるが、DNS接続先の切替とは区別する。

**「FBP側の本番へ配置すること」と「既存ドメインの行先を切り替えること」は別工程。** FBP側の本番URLはDNS切替前でも閲覧可能になる場合がある。noindexは検索登録を抑制する設定であり、閲覧を制限する認証ではない。公開範囲・閲覧制限に明示要件があればそれに従う。

工程の説明は新たな許可を発生させない。開発、本番配置・データ取込み、ドメインのサーバー設定、DNS切替、検索登録について、人間の履歴から現在有効な許可・禁止を引き継ぐ。実施前の工程に必要な許可だけが不足している場合は、その内容と影響を具体的に尋ねる。すべての工程に毎回別承認を要求したり、合意済みの方針を再質問したりしない。自動処理へ渡す場合も実行指示と進捗記録へ残す。

## 初回コメントの承認済みテンプレート

> サイトの移行は、次の順で進めます。
>
> 1. **DNSのTTLを120秒に変更します。【旧サイト表示中】**
>    切替時の待ち時間を短くするため、変更可能な場合は、Webサイト用DNSレコードのTTLを最初に120秒へ変更していただきます。接続先はまだ変更しません。変更前のTTLが切れるまでは、以前の情報が残ります。
>
> 2. **サイトを再構築します。【旧サイト表示中】**
>    元サイトのページ・記事・画像・動画などを確認し、FOCUS上に再構築します。取り込めないものや再現できない部分は一覧でお知らせします。
>
> 3. **FOCUS本番へ取り込み、見比べていただきます。【旧サイト表示中】**
>    ご承認後、FOCUS側の本番環境へプログラムとデータを移します。確認用の本番URLをご案内しますので、元サイトと見比べてください。
>
> 4. **独自ドメインをFOCUS側に設定します。【旧サイト表示中】**
>    DNSを切り替える前に、FOCUS側で独自ドメインの受け口と表示先を設定し、事前確認を行います。
>
> 5. **ご確認・ご了承後、DNSを切り替えます。【ここから一時的に表示できない可能性があります】**
>    ドメインの接続先を旧サイトからFOCUSへ変更します。反映には時間差があるため、旧サイトが表示される方と、新しい接続先へ切り替わる方が混在します。旧サイトをこの時点で停止する作業は行いません。
>
> 6. **SSLを設定し、HTTPSでの表示を確認します。【切替作業中】**
>    DNSがFOCUS側を向いたことを確認してから、SSL証明書の発行・設定を行います。設定が完了するまでは、一時的にサイトを表示できない場合があります。
>
> 7. **新サイトの表示・動作を最終確認します。【新サイト表示中】**
>    独自ドメインで新サイトがHTTPS表示されること、ページ・画像・リンクなどを確認し、移行結果をご報告します。DNSの反映が完了した方から、新サイトが表示されます。
>
> 公開時期と検索エンジンへの登録設定は、ご指定に沿って進めます。

番号・工程の順番・表示状態の区別は維持する。サービス名・顧客が変更するかどうか・既存設定・公開許可・noindex指示は案件に合わせる。すでに完了した作業を再依頼せず、対象外なら理由を添える。未確認のURL・件数・停止時間を約束しない。「公開してください」がどの工程を指すかは履歴を読んで判断し、必要な場合だけ確認する。

## AIの工程管理と進捗コメント

AIは実施前・再開時に最新の顧客履歴、作業領域の工程記録、証拠を読み、同じ7手順の現在地と許可を確認する。以前のAIの発言だけで工程完了を推定しない。前工程に依存する作業は確認が揃ってから進め、独立した準備を並行する場合も未完了工程を残す。

案件の非公開作業領域で、進捗CLIと同じprogress領域に`workflow.json`を保持する。これはAIが更新する工程表であり、既存CLIが自動生成・更新するファイルではない。最初の案内時から作り、各工程の状態変化とコメント送信結果に合わせて更新する。記録項目は、7手順の番号・名称・状態（未着手/作業中/お客様待ち/確認済み/中断/対象外）、現在の未完了工程、実際のサイト表示状態、次の作業、待機理由、許可根拠の履歴ID、証拠の参照、最後に投稿成功したコメントIDと内容の要点。認証情報は記録しない。

取得manifestができたら既存の進捗CLIも使い、[工程との対応](completion.md#7手順と工程記録の対応)で実施結果を記録する。workflow、CLI、最新の履歴・証拠に相違があれば実状態を確認してから更新する。DNSの変更依頼を出しただけで変更済みにせず、顧客の表示確認・DNS完了返信等の確認待ちを残す。CLIの`migration_complete`だけでは、TTL対応や顧客確認まで完了したと判定しない。

進捗コメントは工程の開始・完了、顧客作業の依頼、待機・中断、再開など意味のある変化で送る。同じ状態のまま定期的に重複投稿しない。許可されたTaskコメント工程・既存の投稿機構を使い、投稿成功後にコメントIDを記録する。AI内部の工程ファイル名やCLI名は顧客コメントへ載せない。

> **現在：手順3/7「FOCUS本番への取込み・目視確認」【旧サイト表示中】**
>
> 完了したこと：FOCUS本番へのページ・記事・画像の取込みと、こちらでの表示確認が完了しました。
>
> お客様へのお願い：ご案内した本番URLで、元サイトと見比べてください。現在はご確認待ちです。
>
> 次の作業：ご確認後、手順4の独自ドメインの事前設定へ進みます。DNSはまだ変更していません。

例の完了内容は実際に確認した事実へ置き換える。「現在の工程」と「現在の独自ドメインの表示状態」は別々に判定する。DNS切替後は旧・新の混在やHTTPS未完了をそのまま伝え、全利用者で同時に切り替わった、旧サイトを停止した、停止が必ず発生した等と断定しない。
