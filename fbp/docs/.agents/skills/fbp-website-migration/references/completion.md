# 工程と完了条件

初回案内とAIの実作業・進捗コメントは[承認済みの7手順](customer-flow.md)に揃える。基本の順序は、TTLを最初に120秒へ変更 → 調査・テスト構築 → 許可されたFBP本番へのコード・データ取込みとAI・顧客による目視確認 → 独自ドメインの事前設定 → 許可後のDNS切替 → 必要な証明書発行・SSL設定 → HTTPSでの最終確認。事前設定は本番確認と並行できるが、DNS接続先変更の依頼は両方の準備と切替許可が揃ってから行う。

| 工程 | 確認すること |
|---|---|
| 収集 | 合意範囲・原本・欠落/除外/上限・取得できないデータ |
| 実装 | FBP入口・管理画面・デザイン・フォーム等の作成と確認 |
| データ | テスト/本番の明示取込み、件数・内容・素材・公開範囲の照合 |
| 本番目視確認 | FBP側本番URLの実表示、代表ページ・画像・リンク・必要な動作。お客様へ確認URLと未対応部分を案内 |
| ドメイン事前設定 | 設置先の受け口・公開トップ・www・証明書取得用経路を準備し、DNS変更前に接続先を指定して確認。既存設定は再追加しない |
| DNS | 表示確認と事前設定・切替許可の後、正規名/wwwのA/AAAA/CNAMEと移設先を照合。MX/TXT等を保持。顧客作業なら完了返信を待つ |
| サーバー | 既存conf/証明書/転送、許可された変更、構文検査とreload。DNS一致が必要な証明書発行は切替後に行う |
| 公開 | 証明書・HTTPS・www転送・パス/クエリ保持・代表画面・画像・非公開制御 |
| 通知 | 保存、送信受付、実着信を個別確認。実送信しなければ未実施 |

DNSは実際の権威DNSを管理する会社の画面で案内する。取得元WebサーバーのSSL設定だけへ誘導しない。設定済みなら再変更を求めず、設置先のApache・証明書・公開先を調べる。SSL表示問題は証明書・チェーン・ブラウザーのURL/エラーを確認し、再発行を繰り返さない。

公開切替には対象サーバー・アプリ・ドメイン・保持する設定・バックアップ・戻し方を具体化する。root認証は環境固有の許可条件に従い、通常の実装承認やCLIフラグだけで取得しない。

## 進捗CLI

```bash
python3 scripts/website_migration_status.py --workspace /work/progress init --appcode app-example --plan /work/prepared/migration.json
python3 scripts/website_migration_status.py --workspace /work/progress record --stage production_import --state verified --note '本番取込みと照合を確認' --evidence /work/compare.json
python3 scripts/website_migration_status.py --workspace /work/progress show
```

同じ状態・メモ・証拠でイベントを増やさない。plan変更後はreplanで以前の段階をリセットして再確認する。証拠ファイルの変更・欠落も検出し、その工程を未確認へ戻して集計する。ハッシュは変更検知用で、許可・電子署名・本番操作の証明ではない。

published（コード/データ/DNS/TLS/ルーティング/コンテンツの記録）とmigration_complete（範囲・原本・テスト・バックアップ・通知を含む全体）を分ける。not_applicableは本当に対象外の場合だけ理由を書く。フォームがあるのに送信未確認だから対象外にしてはいけない。

実際に確認した範囲を完了として報告し、未確認の着信等が残れば明記する。コードだけで記事/画像も公開済みとしない。進捗CLIはTaskへ投稿・完了操作をしない。auto-taskでは既存の許可・snapshot・状態遷移を守り、DNS待機や未実施説明だけで同じコメントを繰り返さない。

「FBP本番への移行済み」「お客様の表示確認待ち」「独自ドメインの準備済み」「DNS切替待ち」「HTTPS最終確認済み」を分けて説明する。進捗CLIの既存stageへ証拠・現在地・次の顧客作業を記録し、新しいstageが実装済みだと仮定しない。noindexの維持と解除は合意に従い、DNS切替やコード配布だけで勝手に解除しない。

## 7手順と工程記録の対応

顧客向けの7手順と、CLIの技術的なstageは粒度が異なる。CLIのstage名・完了判定は変更せず、AIは同じprogress領域の`workflow.json`にも7手順の現在地と顧客確認・待機状況を保存する。再開時にはCLIのshow、workflow、最新の人間の履歴と証拠を照合する。manifest作成前はworkflowから開始し、準備できた時点でCLIも初期化する。

| 顧客向けの手順 | 既存CLIへの記録 | workflowに残す確認事項 |
|---|---|---|
| 1. TTLを120秒へ変更 | `scope`のnote・evidence | 実際のTTL、変更済み/変更不可/顧客待ち、変更前のキャッシュ有効期限。TTLを変えずに完了扱いにしない |
| 2. 再構築 | `scope`、`collection`、`implementation`、`test_import` | 取得範囲・欠落、テストの結果 |
| 3. 本番取込み・目視確認 | `backup`、`production_code`、`production_import` | コードとデータそれぞれの照合、AIの実表示確認、顧客への確認依頼と返信。顧客待ちは残す |
| 4. 独自ドメイン事前設定 | `routing`を`pending`としてnote・evidenceに事前確認を記録 | 受け口・表示先・DNS変更前の確認結果。DNS切替・TLSまで確認済みとはしない |
| 5. DNS切替 | `dns` | 切替許可、顧客への依頼と完了返信、実際のDNS一致、表示の混在や不通 |
| 6. SSL設定 | `tls` | 証明書とHTTPS・転送の実確認結果 |
| 7. 最終確認 | `routing`、`content`、必要な`contact_delivery` | 独自ドメインでの最終表示・動作、残件、noindex指示と実状態 |

7手順の確認が揃い、合意範囲の技術的な照合も完了した場合に全体完了を報告する。対象外は理由を記録し、単に未実施・権限不足・顧客待ちであることを対象外に置き換えない。コメントの現在地と工程ファイルを一致させ、投稿成功のコメントIDも保存する。
