# FBP対応範囲リスト

最終確認: 2026-11-14。事前チェック・実装前の共通判断に使う。詳細仕様の正本は各Skillと現行実装。この表は対応範囲の索引であり、対象アプリへの実装済み・契約上の提供・設定済み・利用許可を保証しない。

## 判定方法

- 標準対応: 既存機能・設定で対応できる。実際の設定・権限と着手許可を確認する。
- 追加開発: アプリ側で実装できる。必要な変更許可と該当Skillに従う。
- 条件付き: 必須条件とSkill・実装を照合し、満たす場合だけ進める。
- 非対応: 現行の自動対応では実行せず、理由を返信する。
- 開発者対応: 共通frameworkのコード変更など、顧客タスクで変更できない範囲。既存の開発者引継ぎ経路を使う。
- 未確認: 表にない・根拠不足・実装と表の不一致は非対応と決めつけず、関連Skill・現行実装を必要な範囲だけ調べる。実現可能性を未確認のまま約束しない。

依頼本文・添付・全履歴の現在有効な要求を文脈で判断する。単語一致で拒否しない。セキュリティー制限、明示的な完了・保留、変更・リリース許可、専用の内部制御と状態遷移を優先する。複合依頼は項目別に判断し、対応できる部分だけで依頼全体を完了扱いしない。承認時は判断・根拠・条件・未確認事項をEXEC_INSTRUCTIONに渡す。

## 更新ルール

- 共通機能・ツール・Skillの追加、仕様や制限の変更、対応可否の誤判定を修正したときは、この表への影響を完了前に確認する。影響があれば同じ作業で行を追加・修正し、最終確認日・根拠Skill・条件を更新する。影響がない変更では日付だけ更新しない。
- 対応可能への変更は実装・検証結果を根拠にする。未実装の予定、ツールがあるだけ、過去のAI回答だけで対応可能にしない。非対応の解除では返信ルールも同時に修正する。
- 個別アプリだけの機能はアプリdocsへ記録し、全FBPの標準対応へ昇格させない。アプリ固有の判定条件はdocs/auto-task-policy.mdへ置く。
- 自動ワーカーは共通リストの更新のためにscriptsを変更・停止したり、禁止されたframeworkコード変更をしない。共通ルール更新の権限・共有編集の安全性を確保できない場合は、アプリdocsに「対応範囲リスト更新待ち」として機能・判定・根拠・検証・変更案を残し、開発者への内部報告へ引き継ぐ。更新済みとは報告しない。別保守工程ではこの記録を確認して表へ反映する。
- 表とSkill・実装の不一致を見つけた場合は最新の確認済み仕様を優先し、表を修正するか更新待ちとして明示する。事前チェック中に勝手に機能実装や対応範囲の拡張を行わない。
